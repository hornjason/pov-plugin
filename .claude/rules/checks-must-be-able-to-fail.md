## The rule

Before you trust a check, prove it fails. Break the thing it guards — by hand,
in a scratch edit you throw away — and watch it go red. If it stays green, you
do not have a check, you have a line in a report.

Do this for anything whose job is to catch a problem: a test, a gate, a lint
rule, a ratchet, a CI step.

## Why

This is the single most common defect in this codebase's own tooling. Not a
hypothetical — a count. On 2026-10-06, five of eight issues shipped in one day
were the same bug wearing different clothes: **a check that passed because of
what it never looked at.**

- A prompt-immutability gate ran `ls -lO` and grepped for a BSD flag. On Linux
  CI the command fails, nothing is appended to the violations list, and the
  check passes unconditionally. It had never once run in CI.
- A guard against top-level `require()` stripped template literals with a
  regex. Backticks inside comments and strings paired with unrelated ones and
  deleted 61% of the file, including the two functions the guard existed to
  protect. Two new violations were added and the suite reported 48 pass.
- A budget counter read `parseInt(raw) || 0`. One unparseable byte silently
  meant "zero spent", disabling the cap while every message still looked normal.
- Nine `require()` calls inside `try/catch` in an environment with no module
  loading. Every one threw, every throw was swallowed as a warning, and the run
  reported success with its measurement features switched off.
- A "generator determinism" test called a one-argument function with three
  arguments, compared two arrays that were always empty, and `expect([])
  .toEqual([])` passed no matter how non-deterministic the generator was.

Every one of those was green. Every one was green for a reason that had nothing
to do with the code being correct.

## What makes this hard to notice

A failing check announces itself. A check that cannot fail looks exactly like a
check that is satisfied — and it looks *better* over time, because it never
flakes and never blocks anyone. The quieter it is, the more it is trusted.

Three shapes to watch for, all taken from the list above:

- **Fail-open error handling.** A `catch` that returns "no problems found", or
  a parse failure that defaults to an empty violation list. Anything that can
  throw inside a fail-open guard is a guard bypass; the fail-open is not the
  bug, it is the amplifier.
- **A detector narrower than what it detects.** Text matching that a reformat,
  a line break or a different platform defeats. If the guard's view of the
  input can silently shrink, assert on the view itself.
- **Assertions that hold vacuously.** Comparing two empty collections, matching
  a pattern against text that was stripped out upstream, asserting a value the
  test itself just set.

## In practice

When you add or change a guard, say in the commit or PR **what you broke to
make it fail**. One line is enough: "removing the slice makes it compare the
run against itself, which this now catches." That sentence is cheap to write,
and it is the only evidence that separates a real check from a decorative one.

When a guard has to ship red — a known-violations ratchet — bank progress in
the same commit that earns it, and write down what the number means. A ratchet
nobody can interpret becomes a number nobody lowers.

## A third copy of the spec, and the drift that went both ways (#1)

This repo shipped `specs/POV-SPEC.md` as a hand-retyped copy of a spec that
lives in DailyBriefDashboard. #1568 found TWO copies, picked one, and retired
the other to a stub reading *"Two copies existed and had already drifted."*
There were three. A de-duplication is only as good as the inventory it was
done against, which is an argument for a CHECK rather than for a tidier
inventory — so the copy is now generated by `scripts/sync-spec.ts` and
`test/spec-drift.test.ts` fails when either hash stops matching.

### The drift was bidirectional, and a one-way sync would have deleted a fix

The assumption going in was that the plugin copy was simply stale. Measured,
it was stale in one place and AHEAD in another:

- The canonical rule 10b said voice profiles live at a path under
  `~/.claude/skills/`. That path does not exist for anyone consuming this
  plugin, so the rule was **unsatisfiable off the author's machine** and the
  endpoint that does serve the profile went uncalled. The plugin copy named
  the endpoint. Verified live rather than argued: `GET /api/ae/:name/style-guide`
  returns 200. The fix was ported UPSTREAM before the sync ran.
- The group heading differed only in wording — `Process Rules (SC-41 through
  SC-43)` against `Process (SC-41 to SC-43)`.

**Generating a derived copy makes every local improvement a deletion**, and
the only thing standing between the two is whoever notices before running the
generator. Both differences surfaced as test failures, which is the argument
for writing the checks before writing the sync.

### SPEC-4 pinned a wording, and its own comment said it was about a group

It asserted the verbatim string `### Process (SC-41 to SC-43)`. The defect it
exists for is the group being DROPPED — the retyping lost SC-41 to SC-43, and
SC-43 is the only grader for rule 10b, so the rule survived with nothing
checking it. A test that ALSO fails when "through" replaces "to" is a test
somebody repairs by editing the string, and a real signal gets trained out of
the suite one harmless-looking edit at a time. It matches the property now.

### Two hashes, because they answer different questions

| hash | catches | measurable |
|---|---|---|
| `body-sha256` | someone edited the derived copy by hand | **everywhere** |
| `source-sha256` | upstream moved and nobody re-synced | only beside a DDB checkout |

The source hash cannot run where the source is absent, so that case reports
UNMEASURED in words rather than passing silently.

### Frontmatter is only frontmatter at byte 0

The banner was prepended. Prepending an HTML comment to a file that opens with
`---` does not produce a document with a note on top — it produces a document
with NO frontmatter and a `---` rule in the body. This repo's own
`Spec Discovery` and `HYGIENE-2` cases then could not find `doc-type` or
`updated` in a file that plainly contains both: the parser's view of the input
silently shrank, and everything downstream read "the field is missing" rather
than "the field was not looked for."

`bodyOf` was the quieter half of the same bug. It sliced from the first `-->`,
so moving the banner below the frontmatter would have made it hash the body
MINUS its own frontmatter — a hash that is perfectly stable and about the
wrong bytes. It finds the banner by removal now, so it does not care where it
sits.

## The gate reported the generator's own hash as a leak (an internal issue)

`scripts/sync-spec.ts` writes two SHA-256 hashes into the banner of
`specs/POV-SPEC.md`. The Drive-ID rule was

    /\b[01][A-Za-z0-9_-]{27,}\b/g

and a 64-character lowercase-hex digest beginning with `0` or `1` matches it.
So after the SC-10 re-sync on 2026-10-19 the leak gate reported a Drive ID
that was its own body hash, and two tests went red over content no human
wrote.

**The reason this is an entry and not a one-line fix is that it is a coin
flip.** Two hashes per sync, each with a 2-in-16 chance of starting with a
digit the rule can reach, so about one sync in four is red and the other three
look clean. That is worse than always-red: a gate nobody can predict is a gate
somebody disables, and the clean runs in between are indistinguishable from a
gate that works. The same rule had been sitting over this file since the sync
script landed and had simply never drawn a `0` or a `1`.

**The cause is the detector, not the banner.** `{27,}` is unbounded on top. A
Drive file or folder ID is 28 to 44 characters; nothing longer is one. The
rule was written to say "at least 28" about a thing that has a ceiling, so it
matched every long alphanumeric run in the tree — hashes, base64, anything
generated. This file's third shape is a detector NARROWER than what it
detects; this is the mirror, and both end the same way, with the rule removed
by whoever is tired of it.

Three repairs were considered and rejected, and naming them is cheaper than
having them re-proposed:

- **Exempt the file.** The derived spec is the one file in the tree most
  likely to carry a real Drive ID — the canonical spec cites two, and
  redacting them is the entire reason the redactor exists.
- **Strip the banner before scanning.** That hides anything inside an HTML
  comment from the gate, in every file, to fix one false positive.
- **Shorten the hashes.** Tuning the data to dodge the detector leaves the
  detector wrong, and the next generated artifact trips it again.

Mutations applied by an anchor-asserting substitution that aborts on a no-op
edit, restored from pristine copies immediately after, and both sources
confirmed byte-identical afterwards.
